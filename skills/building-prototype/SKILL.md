# Building Prototype

Turn analyzing-rfp's function list and sitemap into a clickable HTML/CSS/JS prototype of the CLIENT's future software or website — styled with the client's own branding (gathered via QnA), not HBLAB's proposal branding.

## Input

Always sourced from `./output/requirements-summary.md` (client/industry context, for mock data flavor) and `./output/scope-and-sitemap.md` (function list + sitemap) in the current working directory — both produced by analyzing-rfp. Never accept ad hoc replacement input for missing data; redirect to analyzing-rfp instead (see Error handling).

## Process

1. **Check prerequisites.** Confirm `./output/requirements-summary.md` and `./output/scope-and-sitemap.md` exist, and that the sitemap table in scope-and-sitemap.md has at least one real row (not still the empty template row or "*Chưa có sitemap chi tiết*"). If not, stop and tell the user to complete/run analyzing-rfp first.
2. **Resume check.** If `./output/prototype/progress.md` already exists from a previous run, read it — skip screens already marked done, continue from where it left off, don't regenerate from scratch.
3. **Run the UI-kit QnA** (skip if `./output/prototype/ui-kit-brief.md` already exists from a previous run in this project — reuse it instead of asking again, unless the user asks to redo it). First ask the **Loại dự án** classification question in `reference/ui-kit-qna.md` (Hệ thống quản lý vs Landing page/Website marketing thuần) — this decides which branch every step below follows, so ask it directly, don't infer it. If Landing page is chosen, also ask the 3 follow-up questions (L1-L3: mục tiêu chính, trang tham khảo, mức độ animation) in the same file. Then ask the 8 standard questions, derive the product name / product archetype / industry-specific anti-patterns / navigation style / target platform / color palette / typography scale / spacing scale / elevation levels / icon system / support-level / reference products / interface language per its guidance, and write everything (including Loại dự án and L1-L3 if applicable) to `./output/prototype/ui-kit-brief.md`. Generate `./output/prototype/assets/css/global.css` (CSS custom properties for the full palette — primary/primary-dark/tints/accent/9-step neutral scale/semantic-with-bg-tints — plus reusable component classes: button variants (primary/accent/outline/ghost), cards, stat/KPI card with colored accent strip, badge/status pill, table, form inputs, toggle switch, tabs (for in-modal tabs and settings side-nav), colored header/nav surface incl. its collapsed/icon-rail state, a floating collapse/expand toggle button pinned outside the sidebar (`position: fixed`, straddling the sidebar/content edge — never nested inside the sidebar), a sidebar-footer Logout item, breadcrumb, modal, avatar, empty state, toast, plus the browser-chrome theming and hard-ban checklist in `reference/craft-and-qa.md`) from the brief — if Loại dự án is Landing page, skip the sidebar/breadcrumb/settings-side-nav classes that don't apply and instead include the sticky header nav (transparent→solid on scroll) and section-rhythm background classes from `reference/landing-page.md`. Also generate `./output/prototype/assets/js/global.js` with the shared chrome behavior every screen includes (sidebar collapse/expand toggle for Hệ thống quản lý, persisted via `localStorage`, per `reference/screen-generation-guide.md`; for Landing page, the sticky-header scroll listener and `IntersectionObserver` scroll-reveal helper from `reference/landing-page.md` instead). If the target-platform answer is PWA, also generate `./output/prototype/manifest.json` and the related `<head>` tags per `reference/responsive-and-pwa.md`. Before treating the brief as final, run the design critique in `reference/ui-kit-qna.md` ("Điểm nhấn riêng") — reject a generic-safe palette/layout and lock in one client-specific signature moment — and record the result in `ui-kit-brief.md`. If the `frontend-design` skill is installed in this environment, invoke it at this point too for a second, independent pass on the same palette/layout/signature choices (it is optional — the design critique above already carries its core principles inline, so proceed without it if unavailable).
4. **Generate the shared data layer** (mandatory for every project, Hệ thống quản lý and Landing page alike — see `reference/data-layer.md`). Identify the business entities per that file (from `scope-and-sitemap.md`'s "Phân tích đối tượng nghiệp vụ & vòng đời" table for Hệ thống quản lý, or the repeating content types implied by the confirmed sitemap for Landing page), and for each one write `./output/prototype/assets/data/<slug-entity>.js` (schema comment + `const DATA_<ENTITY> = [...]`) — skip any entity whose data file already exists from a previous run, reuse it as-is. From this point on, no screen may hardcode its own copy of business-entity data; every screen includes the relevant `assets/data/<entity>.js` file(s) via `<script>` tag before its own `script.js` and reads from the shared `DATA_<ENTITY>` constant.
5. **Identify main workflows / conversion actions.**
   - **Hệ thống quản lý:** Check `scope-and-sitemap.md` for a "Luồng nghiệp vụ chính (Workflow)" section with already-confirmed workflows (produced by a current `analyzing-rfp` run). If present, use that list directly without asking again. If absent (an older `scope-and-sitemap.md` that predates this section), propose 2-4 candidate workflows from "Danh sách chức năng/module chính" instead, present them, and ask the user to confirm, add, or remove before generating anything. Record the confirmed list — it decides which screens get full interactivity per `reference/interactivity-guide.md`.
   - **Landing page:** There are no CRUD workflows. Instead identify the 1-3 lead-gen/conversion forms in the sitemap (Liên hệ, Đăng ký dùng thử, Đặt lịch tư vấn, Đăng ký nhận tin...), propose them, and ask the user to confirm, add, or remove. Record the confirmed list — these forms get full interactivity per `reference/interactivity-guide.md`, with a successful submit leading to a Trang cảm ơn (Thank-you) confirmation instead of back to a management screen.
6. **Identify the menu grouping / site navigation.**
   - **Hệ thống quản lý:** Check `scope-and-sitemap.md` for a "Thiết kế nhóm menu (Menu Grouping)" table (produced by a current `analyzing-rfp` run). If present, use it directly — it decides the sidebar's accordion group structure per `reference/screen-generation-guide.md`. If absent (an older `scope-and-sitemap.md` that predates this section), derive equivalent groups yourself from the module list (group by business purpose, not technical module name) and tell the user you inferred it. Record the confirmed grouping in `./output/prototype/ui-kit-brief.md` so every screen builds the same sidebar structure and a resumed run doesn't re-derive it differently.
   - **Landing page:** There is no accordion menu — instead decide the shared header/footer navigation per `reference/landing-page.md`: which sitemap pages become top-nav page links (About/Bảng giá/Blog/Liên hệ...) vs anchor-link sections within Trang chủ, and which appear in the footer link columns. Record this nav structure in `ui-kit-brief.md` so every page shares the exact same header/footer.
7. **Identify the entry flow / homepage.**
   - **Hệ thống quản lý:** These two screens anchor the whole prototype's visual quality and are never skipped, even if absent from the sitemap table: a Đăng nhập screen if `requirements-summary.md` implies authenticated/role-based users, or a Trang chủ public screen otherwise; and a Dashboard/Trang tổng quan screen as the landing page right after login. See `reference/screen-generation-guide.md` for what each must contain.
   - **Landing page:** There is no login and no dashboard — Trang chủ itself is the sole entry point. Using the Mục tiêu chính (L1) and trang tham khảo (L2) from `ui-kit-brief.md`, propose a concrete homepage section order (per the structure in `reference/landing-page.md`, trimmed/extended to fit L1), then run the content brainstorming round in `reference/content-brainstorming.md` (headline angle options, which value props to feature, social-proof form, pricing tiers, FAQ questions) — present both the section order and the content framework to the user together to confirm, add, or reorder before generating anything. Record the confirmed section order and content framework in `ui-kit-brief.md`.
8. **Generate the entry-flow screens first.**
   - **Hệ thống quản lý:** Generate Đăng nhập/Trang chủ, then Dashboard, applying the full design-system and anti-wireframe bar from `reference/ui-kit-qna.md` and `reference/screen-generation-guide.md` — every other screen must stay visually consistent with these two. Before continuing, run QA Track 1 (unanchored aesthetic critique, `reference/craft-and-qa.md`) on these two screens against the "Điểm nhấn riêng" locked in `ui-kit-brief.md` and the finishing checklist in `reference/screen-generation-guide.md`; fix them now if the signature moment got diluted or a checklist item was skipped — don't carry the drift into the rest of the sitemap. Then generate the rest of the sitemap table, one screen at a time, per `reference/screen-generation-guide.md` (layout, screen-type content, mock data, cross-screen navigation), `reference/data-layer.md` (every entity read from the shared `assets/data/<entity>.js`, never re-hardcoded), and `reference/interactivity-guide.md` (full interactivity if the screen belongs to a confirmed main workflow, static UI + navigation otherwise): write `screens/<module>/<tên màn hình>/index.html`, `style.css`, `script.js` under `./output/prototype/`.
   - **Landing page:** Generate Trang chủ first, following the confirmed section order and content framework from step 7 and the animation level (L3) from `ui-kit-brief.md`, per `reference/landing-page.md` — write the final copy per the confirmed content framework and any illustrative images per `reference/content-and-seo.md` (SEO/AI-SEO content rules, `<head>` tags, and the search-and-verify process for real, license-free, no-watermark images). Run QA Track 1 on it against the locked "Điểm nhấn riêng" and `reference/landing-page.md`'s own finishing points before continuing — this page carries the whole prototype's visual bar. Then generate the rest of the sitemap table (About/Giới thiệu, Bảng giá, Blog, Liên hệ, Trang cảm ơn, etc.), one page at a time, per `reference/landing-page.md`'s secondary-page guidance, `reference/content-and-seo.md`, `reference/data-layer.md` (repeating content like bài viết/dịch vụ read from shared `assets/data/<entity>.js`), and `reference/interactivity-guide.md` (full interactivity for confirmed conversion forms, static UI + navigation otherwise) — every page shares the exact same header/footer nav recorded in step 6: write `screens/<module>/<tên màn hình>/index.html`, `style.css`, `script.js` under `./output/prototype/`.
   - After each screen (entry-flow included), append a line to `./output/prototype/progress.md` (`- [x] <module>/<tên màn hình>`) so an interrupted run can resume.
9. **Spot-check consistency before finishing.** Once every sitemap row is generated, run QA Track 2 (the countable checklist in `reference/craft-and-qa.md`) on 3 screens/pages from different modules: same header height and behavior (sidebar collapse behavior for Hệ thống quản lý, or sticky scroll behavior for Landing page), same use of Primary-dark for headings/KPI numbers or hero text, same button-style vocabulary (primary/outline/ghost used for the right roles), no screen hardcoding its own copy of entity data instead of using `assets/data/`, plus every countable item in that file. Fix any screen that drifted before moving on — don't report completion with known drift outstanding. Run Track 1 before Track 2, never the reverse.
10. **Generate the entry point.** Write `./output/prototype/index.html`: for Hệ thống quản lý, links to all screens grouped by menu group; for Landing page, either the Trang chủ content itself (the home page is the site root) or a link list in the shared nav order (Trang chủ first) if the sitemap has multiple top-level pages — using the same global styling either way.
11. **Report.** For Hệ thống quản lý: the path to `./output/prototype/index.html`, the total screen count, which workflows got full interactivity, the entry flow (Đăng nhập vs Trang chủ, plus Dashboard), the menu groups used, the signature moment chosen, the target platform, and the navigation style (sidebar vs horizontal/data-grid). For Landing page: the path to `./output/prototype/index.html`, the total page count, which conversion forms got full interactivity, the mục tiêu chính/trang tham khảo/mức độ animation chosen, the confirmed homepage section order, the signature moment chosen, and the target platform.

## Output

`./output/prototype/`, containing:
- `assets/css/global.css`, `assets/js/global.js`
- `assets/data/<slug-entity>.js` — one per business entity, per `reference/data-layer.md`; omitted only if the project genuinely has no repeating entity data
- `index.html`
- `manifest.json` — only if the target-platform answer in `ui-kit-brief.md` is PWA
- `screens/<module>/<tên màn hình>/{index.html, style.css, script.js}` — one set per sitemap row; for Hệ thống quản lý, plus `screens/auth/dang-nhap/` (or the public home screen) and `screens/dashboard/` for the entry flow even when not listed as sitemap rows (not applicable for Landing page — there is no login/dashboard to force in)
- `ui-kit-brief.md`, `progress.md`

Re-running after screens already exist resumes/extends rather than starting over (see Process step 2). If the user explicitly asks to regenerate everything, delete `./output/prototype/` first.

## Error handling

If `requirements-summary.md` or `scope-and-sitemap.md` is missing, or the sitemap has no rows, tell the user to complete analyzing-rfp first and stop without writing output.

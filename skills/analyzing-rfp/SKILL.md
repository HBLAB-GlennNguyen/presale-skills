# Analyzing RFP / Customer Requirements

Turn raw customer input into four structured Vietnamese-language documents that the rest of the presale suite builds on.

## Input

Accept any of:
- An attached RFP/brief file (PDF, Word, or email text)
- Pasted meeting notes or a call transcript
- A short verbal description typed directly by the user (e.g. sales relaying a request in a few sentences)

Sparse input is expected and handled by the interactive verification gate below — don't reject it, and don't generate a mostly-empty summary either. Run the full process.

## Process

1. Read `reference/summary-template.md` and `reference/scope-sitemap-template.md`. They're filled and gated together as one unit and produce two separate output files, kept apart because scope/sitemap is what estimating-effort and writing-proposal read most often and re-edit most.
2. **First pass:** fill in every field in both templates using only information present in the input. Where a bullet field isn't covered by the input, write "*Chưa rõ — xem câu hỏi làm rõ*" rather than guessing. For the "Vai trò & trách nhiệm hai bên" table, leave a row's cell blank (not the marker text) when the input doesn't address it. Do this pass silently — the consultative conversation happens in step 10, not here.
3. **Phân loại loại input:** dựa trên nội dung đã đọc ở bước 2 (độ dài, có đánh số/cấu trúc theo các phần chuẩn của 1 RFP hay chỉ đọc như ghi chú/mô tả rời rạc), đưa ra nhận định phân loại — "Tóm tắt/notes" hoặc "File RFP đầy đủ" — kèm 1 câu lý do ngắn, rồi hỏi người dùng xác nhận hoặc điều chỉnh (dùng AskUserQuestion nếu có, 2 lựa chọn). Ghi nhận kết quả đã xác nhận — quyết định ngưỡng hoàn thiện dùng ở bước 11 (Tóm tắt/notes → 70%, File RFP đầy đủ → 90%).
4. **Draft bổ sung chức năng Master Data & Quản trị hệ thống:** check the function list just filled in "Phạm vi & yêu cầu chức năng" against this checklist — *Quản lý dữ liệu chủ/danh mục*, *Quản lý người dùng & phân quyền*, *Cấu hình hệ thống*, *Nhật ký/Audit log*. For any item not already covered by the input, propose adding it as a draft row and ask the user to keep or discard each proposed item — same confirm-or-reject pattern as the sitemap draft in step 7. Fold the confirmed set back into the function list before continuing.
5. **Draft bảng phân tích đối tượng nghiệp vụ & vòng đời** (in `scope-sitemap-template.md`): using the function list finalized in step 4 and the industry/context already filled in `requirements-summary.md`, draft one row per function that manages a distinct data object (skip functions that only view/report — they don't own data): infer the entity name, a field-count band (Ít/Vừa/Nhiều), a plausible lifecycle grounded in the stated industry (e.g. regulated industries imply certificate/approval-style lifecycles), and any domain-driven constraints. If the industry/client-type fields needed to ground this are still marked "*Chưa rõ*" at this point, resolve those specific fields with the user first (pulling forward that part of step 10's consultative gate) before drafting lifecycles/constraints — don't infer a lifecycle from an unknown industry. Present as a draft table and ask the user to confirm, adjust, or remove rows before treating it as final. Fill the total-count line (or "*Không có đối tượng nghiệp vụ riêng*" if none apply).
6. **Draft bảng "Đối tượng sử dụng & nhiệm vụ"** (in `scope-sitemap-template.md`): using the function list finalized in step 4 and the industry/context already filled, infer the end-user roles who will directly use the future system and each role's main responsibilities, tied to the relevant function/module. Present as a draft table and ask the user to confirm, adjust, or remove rows before treating it as final — same confirm-or-reject pattern as the other draft steps. Fill the total-count line (or "*Không xác định được vai trò người dùng riêng biệt*" if not enough information).
7. **Draft the sitemap** (in `scope-sitemap-template.md`): using the function/module list from step 4, propose a reasonable screen list into the "Danh sách màn hình & Sitemap" table — for each function, infer the screens it plausibly needs (a main screen, a management/list screen if it involves records, form pop-ups if it involves create/edit actions). For entities from step 5 with multi-state lifecycles (e.g. an approval workflow), also consider whether that lifecycle justifies an additional screen (e.g. an approval/state-history screen) beyond the default set. Present this as a draft and ask the user to confirm, add, or remove rows before treating it as final. Fold their answer into the table, then fill the total-count line (Màn hình chính + Màn hình quản lý + Pop-up dạng form).
8. **Xác định luồng nghiệp vụ chính (Workflow) & vẽ diagram** (in `scope-sitemap-template.md`): propose 2-4 main workflows from the function list confirmed in step 4 — present them and ask the user to confirm, add, or remove; this is the list `building-prototype` will read directly later, not re-ask for, so treat it with the same care as the other draft-confirm steps. For each confirmed workflow: state its owning function/module; if that function maps to an entity with a row in step 5's domain-object table, draw a Mermaid `stateDiagram-v2` from that entity's "Vòng đời / trạng thái chính" column — otherwise write "Không áp dụng — chức năng không sở hữu đối tượng có vòng đời riêng" instead of fabricating one. Always draw a Mermaid `flowchart` screen-flow diagram referencing actual screen names from step 7's sitemap table that belong to that function, in a plausible visit order. Fill the total-count line.
9. **Compute completion:** count every fillable field across both templates together — each bullet whose label ends in `:`, plus each row of the roles table, plus the sitemap total-count line, plus the domain object table's total-count line, plus the user-roles table's total-count line, plus the workflow section's total-count line — as one shared denominator. Exclude "Giả định đưa ra khi thông tin chưa đầy đủ" from this count; it's filled later, not client info. Completion % = fields actually filled ÷ total fields × 100.
10. **Interactive verification gate — consultative, not a checklist (run before writing any output file):**
    - If completion is 100%, skip to step 12.
    - Otherwise, close the gaps by talking with the user (the person running the skill, not the client) the way an experienced presale consultant would in a discovery call — not by reading off a list of empty fields. For each area still missing: open with why it matters and, when you have grounds to (industry, client type, engagement model, similar deals already established), offer your own informed take or the common-practice default before asking — then ask one focused question to confirm, adjust, or reject it. One question at a time. Let the conversation branch naturally: if an answer changes an earlier assumption, revisit that field instead of plowing through the remaining gaps in a fixed order.
    - Fields that already have a fixed set of options in the template — loại hình khách hàng, mức độ trưởng thành IT nội bộ, mô hình hợp tác — still get asked as multiple-choice using those exact options (use the AskUserQuestion tool if available); everything else gets the consultative treatment above rather than a bare open question.
    - Fold the user's answers into the templates and recompute completion after each exchange, not just at the end.
    - If an answer during this gate establishes or changes the industry/client type after step 5 already ran, revisit and update the domain-object table's lifecycle/constraint columns to match.
11. **Completeness threshold — ngưỡng động theo bước 3:**
    - Ngưỡng áp dụng: 90% nếu bước 3 phân loại input là "File RFP đầy đủ"; 70% nếu "Tóm tắt/notes".
    - If completion ≥ ngưỡng áp dụng, proceed to step 12.
    - If completion is still below ngưỡng after the gate: tell the user the exact percentage AND the ngưỡng đang áp dụng (kèm lý do — phân loại input ở bước 3), and list which fields remain missing. Ask whether they want to (a) supply more information, or (b) proceed anyway with assumptions.
      - (a): repeat step 10 with the new information, then re-check the threshold.
      - (b): for each remaining missing field, write a reasonable assumption grounded in the fields already filled (industry, client type, engagement model, similar deals) as "*Giả định: <nội dung>*" instead of "*Chưa rõ*" — but only for fields where a genuinely non-fabricated, safe default exists; leave fields that are purely client-owned facts (e.g. decision maker identity, exact budget/dates, specific tech requirements, out-of-scope items, UAT/maintenance ownership) as "*Chưa rõ*" so they still surface as real clarifying questions in step 13. Present the full list of assumptions in one message and ask the user to confirm or correct each one. Fold any corrections back into the templates. Only continue to step 12 once the user has confirmed.
12. Write the two finalized templates to `./output/requirements-summary.md` and `./output/scope-and-sitemap.md` (create `./output/` first if it doesn't exist).
13. Read `reference/clarifying-question-style.md`, including its "Phân loại câu hỏi theo 3 nhóm" section. For every field still marked "*Chưa rõ — xem câu hỏi làm rõ*" (genuinely unknown to the operator, as opposed to fields resolved by assumption in step 11) and every still-blank row in the roles table, write one client-facing question per the style guide: brief expert context/recommendation first, then a Yes/No or 2-4 option question (for a blank role row, the options are who — HBLAB, the client, or shared — owns that responsibility). Do not write bare open questions, and do not invent specific numbers (pricing, exact benchmarks) without grounding — see the style guide's rule on this. Sort each question into exactly one of the 3 categories per the style guide's mapping table, then write `./output/clarifying-questions.md` with 3 sections in this order: "## A. Câu hỏi về thông tin dự án (Sale)", "## B. Câu hỏi làm rõ nghiệp vụ (Domain/BA)", "## C. Câu hỏi kỹ thuật (Technical)" — number questions starting at 1 independently within each section. A section with no questions still keeps its header, with the single line "*Không có câu hỏi ở mục này — thông tin đã đầy đủ.*" instead of being omitted. If all 3 sections would be empty, collapse the whole file to a single line noting the input was fully sufficient instead of showing 3 empty headers.
14. Read `reference/risk-rubric.md`. For each of the 8 risks listed there, score Likelihood and Impact separately (1-5 each, or "?" with a reason if there still isn't enough information — this should be rare after the gate in steps 10-11), using the item's guidance and the general scales. Compute each risk's score (L × I) and band via the matrix table. If a risk's scoring depends on a field marked "*Giả định*", say so in that risk's justification. Write each risk with its L, I, score, band, and justification, then the overall project risk band (the highest band among all 8 risks, naming which risk drives it), to `./output/risk-assessment.md`. Apply the rubric's note on contract model: if risk #1 (scope misunderstood) has Impact ≥ 4 and the client classification section indicates Fixed Price, call this out explicitly as the highest-risk combination.
15. Report all four file paths back to the user, together with the final completion percentage, the input classification and threshold that was applied, and whether any fields were resolved by assumption rather than confirmed fact.

## Output

Always four files in `./output/` relative to the current working directory, always in Vietnamese:
- `requirements-summary.md`
- `scope-and-sitemap.md`
- `clarifying-questions.md`
- `risk-assessment.md`

If `./output/` already contains these files from a previous run, overwrite them — each run reflects the complete current input, not an incremental diff.

## Error handling

If the input has no usable content (empty file, corrupted/unreadable format, blank paste), tell the user directly and do not create the output files.
